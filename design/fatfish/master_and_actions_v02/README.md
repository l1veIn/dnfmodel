## 参考图确实如何传入

走路、施法、首版跳跃均使用 **两张图片**：选定站姿的 `master_feet_reference_8x.png` 加对应的 `references/*_pose_gray_8x.png`。跳跃修正使用 **三张图片**：首版跳跃、原动作灰色姿势参考、选定站姿主帧。

使用原有技能脚本 `C:/Users/A/Desktop/fatfish_game/.agents/skills/65535/scripts/s65535.py`。包装程序为每张参考图传入一次 `--image`；技能脚本读取本地文件，将图像字节编码为 data URI，写入 POST 请求的 `input.image` 数组。因此请求中包含图片数据，并非仅在提示词中提及路径。

`qa/reference_payload_audit.json` 记录了请求体复核：用未修改的技能脚本重建实际请求体，在网络调用前拦截，逐张解码图片并核对 SHA-256；未创建重复任务。所有图片都与原请求记录的字节匹配。实际任务的请求清单和图像哈希保存在 `master.request.json` 及 `requests/*.request.json`。

服务端任务详情不回显输入图片。其 `image_count` 在所有任务中都是 1，不能拿它当作已传参考图的数量，也不能据此认证上游实际读取/遵循了几张图片。这里确认的是客户端提交链路及图像字节；没有把接口不提供的回显证据伪装为已获得。

## 主帧和动作检查

选定主帧简化了金边和发丝纹理，修正了前景左脚较低、背景右脚较高的站姿关系。静态试用检查：人物可见高度 102 像素；眼位相对参考约差 1.7 像素，支撑鞋底约差 0.2 像素。未参与拟合的后脚约差 2.1 像素。人工标点本身约有 1–2 个原生像素不确定性，不能把小数视为引擎级精度。

走路、施法、跳跃分别做了约 -2.44°、+4.14°、-4.03° 的整体旋转，并与缩放、平移合为一次原图到原生画布的变换。没有对局部肢体做变形。使用眼位和支撑脚拟合后，这两个点的数学残差接近零，**不代表整个人物动作已经精确对齐**。

独立抽查（未用于拟合）的误差如下，均为人工目测估计：

| 测试 | 抽查点 | 原生像素偏差约值 |
| --- | --- | ---: |
| 走路 | 两只手 | 3.2 / 4.3 |
| 走路 | 后脚 | 7.0 |
| 施法 | 两只手 | 3.0 / 2.5 |
| 施法 | 抬起的脚 | 5.9 |
| 跳跃 | 后方抬起的手 | 2.7 |

整体配色、鲸鱼耳饰、头饰、长发、围裙鲸鱼和金色裙边的身份较上一轮统一。仍能观察到发卷、围裙形状、尾巴弧度、蝴蝶结及袖口细节的变化。轮廓和动作方向可读，局部手脚还需要修整，尤其走路后脚和施法抬脚。

首版跳跃把参考中的抬肘弯臂画成了伸臂，前倾也过大。提示词里的“手臂后摆”与参考不够一致；已针对这张成功结果做了明确弯臂和躯干位置的修正。首版仍保留供复核，最终展示选用 `jump_fix`。

7 个原始结果全部有真实透明通道、透明四角，无画布裁边。4 个选定结果都完整落在同一原生检查窗口中，边缘清理候选的 alpha 仅为 0/255。

## 关于“不降采样直接缩小”

把图像从 1024 像素变成约 100 像素的角色，无论选择哪种算法，都涉及重新采样；只改变预览缩放比例不会改变 IMG 里的实际像素尺寸。本轮没有先强行减色或额外做一次像素化：先在生成阶段简化源图，输出时做一次尺寸/坐标变换，再清理极淡的透明边缘。

最近邻保留硬边，BOX 面积平均更柔和；两种主帧候选均保存。对照同时包含源图改画、姿势修正与边缘处理的影响，不是纯粹只比较缩放算法的实验。4 倍/8 倍检查图只是整数倍显示，判断实际观感应同时看总览底部的原生尺寸。
